## Key Idea

Most attacks that deanonymize a Tor onion service share one requirement: the attacker must be able to contact the service whenever it wants and observe it over a long time. Guard discovery, clock skew, and traffic fingerprinting all work this way. VaulTor removes that requirement. The provider uploads its web application to a volunteer "vault," which runs it inside an SGX enclave and serves clients through an ordinary onion address. The provider only reconnects, rarely and possibly from different places, when it wants to update content. Remote attestation lets the provider check that the vault is running unmodified code. The enclave also keeps the TLS private key, so clients can verify a certificate hash that the provider publishes, and the vault cannot forge or read the content. Measured over the live Tor network, time to first byte and time to last byte rise by at most 5.7% and 2.9%.

## Critique

The core argument is convincing: an attacker cannot make on-demand connections to a host that is mostly offline, which defeats a whole class of attacks. The weaknesses come from where the risk goes. The vault is now an always-online hidden service and faces every attack the provider escaped, so VaulTor moves deanonymization risk rather than reducing it. That works only if volunteers will accept it, and the authors themselves note that operators may face legal risk. The security analysis is entirely qualitative. Table 1 labels attack scenarios "eliminated" or "diminished," but the paper never models how much an occasional, bulky update session still reveals to a vault that knows exactly when the provider connects. The threat model also excludes side channels, yet this design hands the hardware to a possibly malicious owner with root access, which is exactly the setting where SGX side channels have been demonstrated. Finally, the performance evaluation uses a single laptop, a Python server, and three static pages. Tor's latency is so variable that "within the 99% confidence interval" is weak evidence, and the evaluation never tests the dynamic, multi-user applications the design is meant to support.

## Connections

The paper itself says a vault is "similar to a CDN node" for an onion service. That makes it a useful preview of the CDN paper I present on 12/1: both replicate content onto infrastructure someone else operates, but a CDN adds edge nodes to cut latency, while VaulTor adds an intermediary to cut exposure. It also connects to my [OpenFLAME post](/2026/11/05/openflame/), which likewise delegates service to independently run servers. OpenFLAME leaves trust to each server's own access control, whereas VaulTor makes trust in a stranger's machine checkable through attestation, at the cost of trusting the CPU vendor.
